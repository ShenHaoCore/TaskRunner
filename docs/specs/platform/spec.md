# TaskRunner 开发规格

> status: ready-for-agent
>
> 范围：TaskRunner 调度平台的**行为规格**（v3.0.0 起的纯平台形态）。来源：会话对齐 + 代码事实核对。
> 约定：本文不承诺内部文件路径与代码形状；「完成」以可观察的外部行为为准。

## Problem Statement

把周期性业务任务搬上自动化时，每个业务都重复造同一套轮子：定时触发、启停控制、改执行频率、看执行历史、排查失败。这些诉求与具体业务无关，却总是和业务代码搅在一起——调度坏了修调度，业务变了动调度，运维变更（启停、改 Cron）还得改代码发版。

TaskRunner 解决的是**运维视角**的问题：任务怎么注册、怎么被控制、怎么被观察，而不关心任务本身做什么。业务只实现「到点要干什么」，其余全部由平台接管。

## Solution

一个基于 Hangfire 的 .NET 9 任务调度平台：

- **任务即插件**：业务程序集实现周期任务契约、标注默认 Cron，放进宿主的程序集列表即被自动发现并注册为周期作业；平台与业务零耦合（业务模块可独立存在或移除）。
- **运维零代码**：所有任务的启用/停用、立即触发、执行频率调整通过 REST API 与 Dashboard 完成，配置持久化在数据库，重启不丢。
- **观察面**：Dashboard（Hangfire 原生）看作业状态、重试与历史；REST 提供任务清单、统计、单任务执行历史。
- **安全边界**：Dashboard 与 REST 共享一个管理员密钥鉴权；提供只读模式，冻结期拦截一切写操作。
- **两种部署形态**：开发时 Api 单进程既入队又执行；生产时 Api 只入队/出 Dashboard，Worker 独立进程执行，可独立伸缩。
- **存储收敛**：单一 PostgreSQL 库，业务配置与调度引擎各占独立 schema，启动时自动建表。

## User Stories

1. As a 业务开发者, I want 实现一个周期任务接口并标注默认 Cron 表达式, so that 到点平台自动执行我的任务
2. As a 业务开发者, I want 给任务标注互斥执行, so that 上一轮没跑完时下一轮不并发重叠
3. As a 业务开发者, I want 任务执行中上报进度, so that Dashboard 里能看到执行到了哪一步
4. As a 业务开发者, I want 把我的业务程序集追加进宿主的额外程序集列表, so that 平台自动发现并注册我的任务，无需改平台代码
5. As a 运维人员, I want 查看全部任务清单（含启用状态、Cron、下次执行时间）, so that 掌握平台当前在跑什么
6. As a 运维人员, I want 查看任务执行统计与单个任务的执行历史, so that 评估任务健康度、定位失败原因
7. As a 运维人员, I want 一键停用/恢复某任务, so that 业务窗口期暂停任务、窗口结束恢复
8. As a 运维人员, I want 修改任务的 Cron 表达式（含合法性校验）, so that 不改代码发版即可调整执行频率
9. As a 运维人员, I want 立即触发一次任务, so that 改完配置当场验证执行结果
10. As a 运维人员, I want 每次执行在 Dashboard 有连续输出与耗时, so that 排查失败时有现场
11. As a 管理员, I want Dashboard 与 REST 全部要求管理员密钥（header/cookie/Basic 任一）, so that 运维面不对未授权者开放
12. As a 管理员, I want 开启只读模式后所有非查询请求被拒绝, so that 发布冻结期运维面天然只读
13. As a 部署者, I want 生产拆成 Api（入队+Dashboard）与 Worker（执行）两个进程, so that 入队压力与执行压力互不影响、可分别伸缩
14. As a 部署者, I want 启动时自动建业务表与调度引擎的表, so that 新环境零手工 SQL 即可拉起
15. As a 部署者, I want 已成功的作业记录自动过期清理, so that 调度库不无限膨胀
16. As a 部署者, I want 重复任务名在启动期即报错, so that 配置冲突不会潜伏到运行期

## Implementation Decisions

- **任务契约**：单方法异步执行接口 + 标注特性声明默认 Cron / 名称 / 描述 / 启用状态；互斥执行与进度上报均为可选特性标注，不标注则用空实现兜底。契约与调度引擎隔离——业务只依赖契约层，不感知 Hangfire。
- **发现与注册**：启动期扫描宿主程序集与额外程序集，凡标注默认 Cron 的任务类型即生成稳定 JobId 并注册为 Hangfire 周期作业；启用状态、Cron 覆盖值以数据库为准，特性标注值仅为首次落库的种子。
- **配置持久化**：单一业务表存任务的启用状态与 Cron 覆盖；EF Core 迁移自动建表；调度引擎表由 Hangfire 在独立 schema 内自建。
- **调度引擎**：Hangfire 1.8 + PostgreSQL 存储；轮询间隔、成功作业保留时长、控制台跟随保留策略由共享配置统一下发；存储标识校验失败即启动失败（fail-fast），不允许带错误配置运行。
- **鉴权**：共享管理员密钥三种等价携带方式（请求头、cookie、Basic）；Dashboard 用授权过滤器、REST 用认证方案，密钥未配置时启动告警。
- **只读模式**：API 全局动作过滤器拦截非 GET 请求；配置键与 Dashboard/REST 鉴权同源。
- **Cron 输入校验**：运维接口对 Cron 做语法与安全边界校验（拒绝非法或越界的高频表达式），校验失败返回明确错误信息。
- **宿主角色**：同一套宿主装配按角色分化——Api 角色注册入队与监控读侧，Worker 角色注册执行侧；开发模式下单进程双角色。

## Testing Decisions

**好测试的定义**：只测外部可观察行为（API 响应、公开服务返回、数据库可见状态），行为不变则测试不变；期望值来自独立真源（已知字面量、演算过的例子），不用被测代码同法重算；同一缝上一测试一实现交替推进。

**测试缝（已确认 2026-10-26）**：

| 缝 | 层级 | 能抓到 | 漏掉 |
|----|------|--------|------|
| **REST `/api/tasks` 全部端点**（主缝，覆盖鉴权与只读过滤） | 最高公开边界 | 运维行为的端到端正确性：启停/Cron 覆盖/触发的持久化效果、鉴权拒绝、只读拦截、Cron 校验错误映射 | Dashboard 渲染细节、纯展示统计口径 |
| **Core 公开服务**（任务仓库与任务目录） | 公开边界 | 契约扫描发现规则（标注/未标注/重复 JobId）、启用与 Cron 覆盖读写、Cron 校验边界 | HTTP 层映射错误（由主缝兜住） |

**仓库内同类测试先例**：`TaskRunner.Tests` 已有 23 个测试，全部落在 Core 副缝——Cron 守卫 8 例（5/6 字段与简写接受、非法拒绝）、扫描发现 2 例（忽略未标注/抽象、无内置任务）、JobId 生成 2 例、仓储 Sync/清理 3 例、执行器成功与失败路径 2 例、分层边界守护 6 例；测试用真实 SQLite 内存库验证 SQL 行为，不 mock 被测事务边界——与本 spec 的「只 mock 外部系统」红线一致。REST 主缝暂无覆盖，已切票 [02](issues/02-运维REST契约.md)、[03](issues/03-鉴权与只读拦截.md) 待领取；票进度见 [specs 索引](../README.md)。

## Out of Scope

- 业务任务的具体实现（示例任务已随 v2.0.0 移除；平台不内置任何业务任务）
- 多租户、任务级权限隔离（鉴权模型即单一管理员）
- Dashboard 的界面定制与主题
- 分布式部署的存储级调优（跨实例锁争用、存储分片）
- 非 Hangfire 的调度引擎适配层
- PostgreSQL 之外的其他存储提供程序

## Further Notes

- 演进约束：破坏性变更（任务契约、配置键、业务表结构）升 major；其余按语义化版本。
- 分支与发布流程见 `CONTRIBUTING.md` 与 [branch-management.md](../../branch-management.md)；升级注意事项以 Release 说明与 `CHANGELOG.md` 为准。
- 业务插件回归路径：历史版本保留完整示例实现，可按 README 的插件说明拆成独立程序集经额外程序集注入，平台侧无需改动。
